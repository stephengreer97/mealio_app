Account and subscription

Read off screens/account/AccountScreen.tsx, lib/purchases.ts and navigation/MainTabs.tsx. Three purchase stores and two sign-out scopes. The Admin tab is gone (2026-09-05): its only content was fixture capture, a WebView that read outerHTML and posted it to a dev server, and no rail has read markup since 2026-09-01. Browser-based capture in tests/fixture-runners/capture-fixtures.ts replaces it.

2026-09-04 — Amazon Fresh is gone. It was the last store with no network rail, so it could only search and hand the user the page to add from. Removed from the catalogue rather than carried as the one store Mealio cannot add to. Every store here now has a rail; the last DOM read in production went with it, and "assisted" is now a state a store passes through (rail off, or unable to answer) rather than what a store IS.

Why the manage-subscription fork exists

A store subscription can only be managed on the platform it was bought on. Calling the native manage UI for the other store throws ("this method is not available in the current platform"), so the native call is only made when the purchase store matches the device — and otherwise the user is told where to go, with a web link as the escape hatch. The fifth arm covers the case RevenueCat does not know about at all: a Stripe or web-only subscriber, who gets the billing portal in an in-app browser sheet rather than a hand-off to the system browser.

Notifications: one grant, and a choice inside it

The Account card's switch is the OS-level one. Turning it off revokes the device token server-side, so sends stop — that half has always worked. What did not exist until MEAL-217 (2026-09-05) was any way to say yes to one KIND of notification and no to another, and it did not exist because nothing was ever sent: sendPushToUsers had no production callers, and the admin broadcast wrote an in-app banner rather than a push.

Per-category choices live in user_profiles.notification_prefs (jsonb), and absent means ON — every account predates the column, so reading a missing preference as off would ship the feature to nobody while looking like a broken sender. The master switch is stored separately from the per-category flags rather than by writing false into all of them, so turning it back on restores what the user chose instead of flattening it.

The settings sheet is offered only while notifications are ON, and its category list comes from the SERVER with the values — a list baked into the app goes stale the moment a build ships, and a creator-only category is not offered to someone who is not a creator. Every product send should go through sendPushToCategory, which is the layer that asks for consent; sendPushToUsers knows about devices, and a device grant is not the same thing as wanting this.

Two cookie clears, not one

CookieManager.clearAll is called with both true and false. On iOS those are two different jars — WKWebView's own store and the shared NSHTTPCookieStorage — and store auth cookies are HttpOnly, so nothing else reaches them. On Android the argument is ignored and the second call is harmless.

Kroger is the exception that has to be handled separately: it is an OAuth connection held server-side, not a cookie in a jar, so "log out of all grocery stores" disconnects it explicitly. Otherwise the button would quietly mean "all stores except the one that is not a WebView".

The admin tab is one repo boundary away from a test harness

fixture-capture-config.ts is shared verbatim between the Node/Playwright capture runner and this screen, and is deliberately dependency-free — no React Native imports, no Playwright imports — so both runtimes can pull it in. The reason the app has a capture path at all is that a real iOS WebView's DOM is not the DOM Playwright sees, and the fixtures are what every store's spec runs against.

The dev-server URL lives in SecureStore because that is the storage this app already has; the value is not a secret.
