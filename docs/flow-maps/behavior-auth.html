The shape of the whole thing

The server issues one long-lived access token (90 days) and no separate refresh token — /api/auth/renew takes a valid access token and returns a fresh one. Storage is expo-secure-store (the device keychain). Everything else here exists to answer one question correctly: who is the app right now?

Two cross-account bugs, running in opposite directions

MEAL-146 — the account boundary. loginWithToken is called from an app-wide deep-link listener with no signed-in check, so account B could take over from A without a sign-out in between. The console ring buffer deliberately retains product names and cart contents, and a bug report attaches it; the last cart run is the key that joins such a report to an account's automation rows. Neither may follow the previous person into the next person's report. The fix is beginSession — the single seam every door goes through — with endSessionDiagnostics called from both boundaries rather than copied, because the two boundaries drifting apart is exactly what MEAL-146 was.

MEAL-155 — the install order. The reverse: B's token was written to the keychain and then verified, because verify reads from the keychain like every other request. A transient verify failure left B's token installed while user was still A — every request from that moment authenticating as B, A shown B's meals under A's name, with no visible transition and beginSession never running at all. Passing the token explicitly is what lets the check happen before anything is committed.

Three orderings that are load-bearing

OrderWhy
teardown before setUserthe instant React commits B, B's session starts — the creator check, the RevenueCat identify, every screen keyed on user?.id. A clear that has not happened by then clears B's fresh state, not A's stale state. (A synchronous move below setUser changes nothing — React batches. It is the deferred form that is real, and that is what the test pins.)
userRef.current kept in step, in both directionsso a second call landing before a re-render compares against the account this one just installed — and a sign-in landing during sign-out's round trips sees that nobody is here
unregisterDevice first at logoutafter the token is cleared the call can no longer authenticate, and the device keeps receiving the old account's pushes

Keyed on the id, never on the object

A token renewal or a profile refresh hands down a new User object for the same person. Tearing their session down for that would be a new bug of the same family, so the switch test is previous.id !== nextUser.id.

What is deliberately not decided here

An expired link and a dead network both throw out of loginWithToken, and both callers currently swallow it or show a generic sign-in failure. Telling the two apart is a product question, not a correctness one — and inventing the copy inside the auth context would be the wrong place for it either way.
