The gate says why, per item (MEAL-202)

It used to carry one blanket sentence for every item — "this may be because the item is out of stock or the store no longer carries it" — a guess covering two possibilities out of five. The network rail reports a real per-item reason, so the screen stops guessing.

The distinction is not cosmetic. "Out of stock" and "no exact match" ask the user for completely different things: the first is nothing they can fix by choosing better, the second is exactly that. A screen that says the same for both sends half its readers to do the wrong thing.

The blanket sentence still appears, but only for an item whose reason has no honest sentence — where every item can say why, a guess underneath them offers two explanations for problems already named, and one of them will be wrong.

The three routes

There were five. Four of them clicked, and they are gone: the sequential page walk, the parallel search pool, the fused search-and-add pool, and the pre-search parking pool. What is left is honest about what it can do — a store either has a rail, in which case Mealio adds and can prove it, or it does not, in which case Mealio searches and the USER adds.

It funnels into finishParallelAdd, which is what the add pool calls. So the reconcile, the review routing, the done screen and the telemetry cannot tell a network run from a pooled one — an item with no exact match becomes an unsuccessful AddResult carrying its candidates, exactly what a pool worker produces, and reaches review by the ordinary road.

Measured on a device, twelve ingredients: 10.8 s tap-to-reconcile against 22.5 s for the pooled path, and the search half of that is 1.0 s for all twelve terms. It also runs no worker WebViews, which is roughly 187 MB of the memory peak.

Both switches are required together. Searching over the network and then clicking to add would load no page for search and then one per item anyway — slower than either path alone.

Why spaSearch exists at all

An SPA storefront changes its URL via pushState and fires onLoadEnd more than once for one route change, while the injected script is still running. Without the flag the engine reads that second same-URL load as a script-killing reload and re-injects — spawning a duplicate SEARCH_AND_ADD_RESULT that over-advances the item index. The concrete damage differs per store and all of it is silent: on H-E-B the skipped item's slot was consumed and the after-snapshot fired while a search page was still up, reporting 0 items; on Walmart the duplicate double-added, then the next item's navigation race-cancelled the cart POST so the item reverted to zero and overwrote the next item's result slot.

Three timeouts, cleared together

searchTimeoutRef, addTimeoutRef and loginCheckTimeoutRef are cleared as a set whenever the engine leaves the flow — entering robot_challenge, or ending the run. A surviving timer fires into a step that no longer exists and advances an index nobody is reading.

Where the other maps pick up

StepDetail lives in
login_check / logineach store's map — this is where they differ most. A store with a network rail is asked over the network in all THREE places that decide login: the silent prewarm probe, this step, and the re-ask that fires on every page load while the user sits on login (reinjectLoginCheckOnNav). The third is the one that starts the run — its verdict calls the before-snapshot directly — so a wrong "signed in" there begins an automation underneath a user who has not signed in yet, which is exactly what was reported from the device. The DOM check is the fallback, reached when the session probe cannot answer — nearly always a page that has not finished its bootstrap, which is not a signed-out user and must never be reported as one
