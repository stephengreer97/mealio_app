The cart engine — one state machine, six storefronts

Read off components/WebViewCartSheet.tsx (5,657 lines) and context/CartJobContext.tsx. The per-store maps show what happens inside a step; this is the skeleton they all hang on.

2026-09-04 — the open, and the review screen

Opening the sheet now NAVIGATES. It used to write the landing URL into state, which on a re-open for the same store is the string the WebView already holds — so React saw no change, the WebView did not move, and no onLoadEnd fired. The open then cleared lastLoadEndUrl, so onStorePage() answered false forever and every phase that waits for the page waited out its whole budget. Measured on a second Wegmans open: the before-probe lost its baseline at 15s and the session handed the user manual searches at 30s, with a session that had written twelve items a minute earlier. It goes through navTo now, whose cache-buster is strictly increasing so two navigations in one millisecond still differ.

A review opens on the first candidate it can ADD, not on row 0. An out-of-stock product cannot be added on a review, so preselecting one gave two disabled buttons whose only explanation was about the quantity — and setting a quantity removed even that. The disabled state now says why, stock before quantity. See lib/review-selection.ts.

The quantity is ASKED FOR, not demanded in advance (MEAL-218, 2026-09-05). The label, the number and a hint line all used to be red the moment the screen opened, so the colour said the same thing whether or not anything was wrong — which is how it came to mean nothing, and how the button beside it came to read as broken rather than blocked. Now: an unset quantity renders as a DASH (a 0 looks like a value someone chose), nothing is red on arrival, and pressing the button with no quantity set flashes the stepper — around the control to press, not around the number. The button therefore stays PRESSABLE while it refuses, which is load-bearing rather than cosmetic: a disabled Touchable never receives onPress, so it can neither answer the user nor be tested. Only when the quantity is the only blocker; if no product is picked either, flashing the stepper would point at the wrong control. See lib/qty-prompt.ts.

2026-09-04 — the sign-in screen, and where the repair may not go

ONE DOOR TO THE LOGIN STEP. There were five routes to it, each deciding for itself whether to navigate first, and the two a RAIL store actually takes navigated nowhere — they set the step and left the WebView on robots.txt. On the device that was the words "Log into your H-E-B account once and Mealio won't ask again" over a blank white page, with nothing to type into. Every rail store parks on the quiet page, so it was every rail store. All five routes now go through surfaceLogin(), which asks canSignInHere (lib/login-page.ts): navigate to the store's login URL unless the page on screen is one you could sign in ON. The skip still exists for the store whose check opened a sign-in menu — it just asks the right question.

THE SESSION REPAIR STOPS AT THE LOGIN STEP. It navigates, and there the page it would navigate away from is a form with the user's typing in it — and an unanswerable session is guaranteed, because H-E-B's sign-in is on accounts.heb.com and the probe is cross-origin. Measured: the repair pulled the user back to the storefront two seconds after handing them the form. The login poll covers that step instead. Same rule as challengeMayTakeTheScreen: a run may be interrupted, a person may not.

2026-09-04. The over-add check's "explained" list now includes what the run tried and was refused, not only the unverified weight lines. See the reconcile map for the measurement.

2026-09-04 — where a failed add goes, and when to believe "signed out"

ANY PROBLEM ADDING IS A REVIEW. The reconcile already routed its definitive failures there. What did not was the RETRY path: an item it thought it could fix, retried, and still could not get went onto the done screen as "Could not add: X" — the one place the user can do nothing about it. Those become review cards now, with whatever the search already found, and a refusal the screen cannot otherwise explain says so rather than naming a cause we do not have.

The one exception is a CAP. "You already have fifteen of these" is not a question about the product, so no other product answers it: quantity_limit_reached keeps its own banner and never becomes a review card.

A SIGNED-OUT ANSWER FROM THE QUIET PAGE IS NOT FINAL. Albertsons cannot resolve a session from robots.txt until its own JavaScript has run once — /userinfo answers 200 with no token, which on a real page IS the expired-session answer. Measured: it said signed out for six seconds about a signed-in user, who was shown a sign-in wall and then signed in by himself. The site gets one storefront load before that answer is believed. This reverses the earlier "act on a signed-out early answer immediately" rule, which was right on its own reasoning and wrong when the answer is wrong.

2026-09-04 — the review fires ONCE

A review pick is written as a top-up, so it finishes through the same netFinalize that routes a failed top-up back to review — the shape of a loop. Two locks stop it: netReviewAddRef marks the in-flight top-up as a review pick, and the card a failure would add carries the item's own term, which is already in the queue. Either alone holds; removing both re-opens the review. So a substitute the store also refuses lands on the DONE screen — the user has already been given the choice this run has to offer.

Review cards created by that routing take their candidates from netCandidatesRef (the search, keyed by term) with the ingredient-name fallback behind it. Reading them off the ADD result gave every card an EMPTY list, because that handler stores candidates: [] on every row it writes.

2026-09-04 — no store chosen is a PROMPT

session_no_store used to hand the user the storefront and a list of terms to search by hand. It now stops the run, shows the storefront, and asks: "Choose a <store> store in the browser below, then tap Try again — prices and what is in stock are different at every store." The WHY is in the banner on purpose; "choose a store" alone reads as busywork.

It reuses the robot_challenge screen because the shape is the same — the page needs a person for a moment, then the run resumes — and Try again already restarts from the login check, which re-reads the session and picks up the store they chose. The banner is the only difference between the two cases.

Four of the five rails need a store; Walmart says needsStoreId: false and never reaches this, because its search is national and its cart is the account's.

2026-09-04 — Amazon Fresh is gone. It was the last store with no network rail, so it could only search and hand the user the page to add from. Removed from the catalogue rather than carried as the one store Mealio cannot add to. Every store here now has a rail; the last DOM read in production went with it, and "assisted" is now a state a store passes through (rail off, or unable to answer) rather than what a store IS.

The gate says why, per item (MEAL-202)

It used to carry one blanket sentence for every item — "this may be because the item is out of stock or the store no longer carries it" — a guess covering two possibilities out of five. The network rail reports a real per-item reason, so the screen stops guessing.

The distinction is not cosmetic. "Out of stock" and "no exact match" ask the user for completely different things: the first is nothing they can fix by choosing better, the second is exactly that. A screen that says the same for both sends half its readers to do the wrong thing.

The blanket sentence still appears, but only for an item whose reason has no honest sentence — where every item can say why, a guess underneath them offers two explanations for problems already named, and one of them will be wrong.

There were five. Four of them clicked, and they are gone: the sequential page walk, the parallel search pool, the fused search-and-add pool, and the pre-search parking pool. It funnels into finishParallelAdd, which is what the add pool calls. So the reconcile, the review routing, the done screen and the telemetry cannot tell a network run from a pooled one — an item with no exact match becomes an unsuccessful AddResult carrying its candidates, exactly what a pool worker produces, and reaches review by the ordinary road.

Measured on a device, twelve ingredients: 10.8 s tap-to-reconcile against 22.5 s for the pooled path, and the search half of that is 1.0 s for all twelve terms. It also runs no worker WebViews, which is roughly 187 MB of the memory peak.

Both switches are required together. Searching over the network and then clicking to add would load no page for search and then one per item anyway — slower than either path alone.

What every request now reports

Since MEAL-219 the retry helper posts a NET_REQUEST for every request any rail makes, and the engine turns it into a telemetry row carrying httpStatus, phase, attempts and rail as columns. It is emitted from the helper rather than from each rail's per-item report because that is the one place all five rails meet — and because attributing a status to an ITEM is wrong under concurrency: H-E-B writes three at a time, so the request in flight is not the item being reported.

Phase is an argument, not a lookup. The first version derived it from a name → phase map inside each rail's prelude, and a prelude is in every script that rail emits — so the cart-read and add scripts began carrying the session probe's operation name, and a test counting session probes by that name went from 0 to 1. Naming an operation in shared script text puts it in every script that shares it, comments included.

Why spaSearch exists at all

An SPA storefront changes its URL via pushState and fires onLoadEnd more than once for one route change, while the injected script is still running. Without the flag the engine reads that second same-URL load as a script-killing reload and re-injects — spawning a duplicate SEARCH_AND_ADD_RESULT that over-advances the item index. The concrete damage differs per store and all of it is silent: on H-E-B the skipped item's slot was consumed and the after-snapshot fired while a search page was still up, reporting 0 items; on Walmart the duplicate double-added, then the next item's navigation race-cancelled the cart POST so the item reverted to zero and overwrote the next item's result slot.

Three timeouts, cleared together

searchTimeoutRef, addTimeoutRef and loginCheckTimeoutRef are cleared as a set whenever the engine leaves the flow — entering robot_challenge, or ending the run. A surviving timer fires into a step that no longer exists and advances an index nobody is reading.

Where the other maps pick up

StepDetail lives in
login_check / logineach store's map — this is where they differ most. A store with a network rail is asked over the network in all THREE places that decide login: the silent prewarm probe, this step, and the re-ask that fires on every page load while the user sits on login (reinjectLoginCheckOnNav). The third is the one that starts the run — its verdict calls the before-snapshot directly — so a wrong "signed in" there begins an automation underneath a user who has not signed in yet, which is exactly what was reported from the device. The DOM check is the fallback, reached when the session probe cannot answer — nearly always a page that has not finished its bootstrap, which is not a signed-out user and must never be reported as one
