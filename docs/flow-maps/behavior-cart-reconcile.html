Reconciliation — trust the cart, not the workers

Read off lib/cart-reconcile.ts (1,557 lines, and every one of them a case somebody hit). Shared by every WebView store. This is the layer that decides what the done screen is allowed to say.

2026-09-04 — a refused item is not an unintended one

A definitive failure (out of stock, no results, needs a weight) routes out of the quantity matching, so it accounts for NOTHING — and a store that accepts the write and flags the line unavailable then leaves a cart row nothing explains, which the over-add check reports as "your cart has 1 item Mealio didn't intend to add". Measured on Albertsons: the row named was the cheese Mealio had asked for by name seventeen seconds earlier. attemptedFailureNames now explains those rows, one unit per failed attempt.

The safety net is unchanged for the two cases it exists for: a product the run never mentioned is still reported, and a DOUBLE-add of something it did add is still reported — only FAILURES are named, and a successful item is already accounted for at its full requested quantity.

2026-09-04 — the cart-query rail is deleted. heb-cart-query.ts had been unreachable since the H-E-B selectors and login check went: its only importer in src was heb.ts, which lost the import that day. 1,299 lines of shipped-but-dead code, holding the LAST querySelector in the codebase. MEAL-14's capability is superseded rather than lost — heb-network-search reads the cart before and after its own write and verifies each line against it.

What remains of DOM access anywhere: ALDI string-searching document.documentElement.innerHTML for a shopId (with a fetch fallback), and Walmart doing an indexOf for <script id="__NEXT_DATA__" in a body it fetched itself. Neither is a selector and neither is on the add path.

Why there is exactly one message

The done screen used to carry two warnings from two observers: "Could not add: X", sourced from the run's own per-item reports, and a cart-check banner sourced from the before/after snapshot diff. The second existed because the first is known to lie — which made them a claim and its own rebuttal, printed as peers, leaving the user to work out which to believe.

The snapshot is the source of truth. The run's reports are consulted in exactly one case: when there is no snapshot to read, where saying so out loud beats quietly reverting to the weaker source. cartBacked is the flag that keeps the two honest.

Conservatism is a requirement, not a style

The original snapshot check recorded its own safety property: the comparison can only under-warn, never false-positive. Promoting the snapshot to sole arbiter makes its false positives the only thing a user sees, so that property is restored deliberately — every clause reports what the cart shows, and nothing is inferred from a silence.

Why exact name matching, and nothing looser

The add path finds a product card by exact name — scoreMatch must return 100 for the add gate to fire — so the title that reaches the cart is the term we searched for. IntendedItem.name is not an approximate label for the product; it is the product's title, and equality against a cart row is a fair comparison rather than a lucky one.

The version this replaced matched on a 60% token overlap, and every false statement the cold review found came out of that leniency: "Bananas" swallowing "Bananas Organic"; a substitute sharing no tokens with its search term landing in two clauses of one sentence about one product. A looser matcher cannot be made safe by filtering its output, because the mistakes are indistinguishable from findings. Exact equality has one failure mode, it is inspectable, and it fails toward silence: a title that does not match is a product we do not claim anything about.

The same findings, said twice, on purpose

message names every product inline and is what the funnel and the tests read. title and detail are the same facts split at the seam the banner collapses on. The verdict — how many, and that something needs attention — must survive collapsing; only the list may fold away. A single blob cannot be elided that way without hiding the fact that anything is wrong, which is the one thing the banner exists to say.

Why the good direction gets copy too

The shape: a stale badge fails every worker, the after-probe reads the cart, and everything is there. Nothing is absent, short or unintended — so there is no warning to print — while the headline, driven by the run's own confirmed count, still says "No items were added." That headline is itself a run-sourced failure claim, and dropping the recovery copy removed the only thing that ever contradicted it. The user re-adds a full cart by hand. So the cart speaks up when it disagrees with the run in the good direction as well.

Two float tolerances that are not judgement thresholds

WEIGHT_EPSILON_LB = 1e-4 and CLICK_EPSILON = 1e-3 absorb the arithmetic and nothing else. The store does not round these lines: the weight a cart row reports is one of the discrete options the row offers, chosen when the line was set, so N clicks × the increment lands exactly on an option. A tolerance wide enough to hide a missed click would be the wrong shape of answer — a missed click is exactly what the check exists to catch.

The invariant behind qty-step exclusion

isZeroedOut carries a sold-by-weight exception keyed on purchaseWeight. On a surface whose item type has no such field the exception is unreachable, and the predicate reduces to a plain productQty > 0 filter — which is what makes the Kroger path provably unchanged by MEAL-65. That is why the Kroger item type deliberately carries no weight fields, and why the type is exported so a test can pin it.
