Three independent reasons ranking cannot affect a cart

  1. It is never called on the add path — only in the isChooseFlow branch.
  2. The choose flow adds nothing. Picking a product saves it as the ingredient's searchTerm; a later run still has to clear the same exact-match gate.
  3. It reorders. It never adds, removes or edits a candidate — the set of products the user can choose from is byte-for-byte what the store returned.

That is why the ranking lives in its own module and not in _scoring.ts: scoreMatch is copied verbatim into six injected store scripts, and each store's add gate is scoreMatch(term, name) === 100 or the equivalent equality. Changing _scoring.ts risks widening or narrowing what the add gate accepts, which is the one governing-principle breach this work could cause.

What the intro sheet is for

Choose Products is a new user's first real interaction with Mealio: up to a dozen modal screens in a row, each asking which store product matches an ingredient. Read cold it looks like the cart being filled one slow item at a time — which is why people abandoned it halfway. They thought they were watching the shopping happen, and it was taking forever.

It is none of those things: it is one-time matching, it saves, and it puts nothing in the cart. The sheet says that before the run rather than on the completion screen where the reassurance used to live. It explains; it does not gate — "Choose products" starts the same flow the floating button always started, one tap away, and it shows once per device either way.

Two spelling bugs the collapse fixes (MEAL-160)

The veto is a set-membership test on tokens, so it is only as good as the agreement between how a shopper writes an ingredient and how a store writes a product. lowfat and nonfat sat in the critical set as single tokens while the normalisers turn every hyphen into a space, so they misfired in both directions at once:

Query vs productScoreWhat went wrong
"low fat cottage cheese" vs "Full Fat Cottage Cheese"75tokenises to low+fat, neither critical — the entry protected nothing
"lowfat cottage cheese" vs "Low-Fat Cottage Cheese"0the right product scored zero
"grassfed beef" vs "Grass Fed Beef"0same shape, two-token entry

Collapsing every spelling to one canonical token on both sides before the membership test makes the entry mean the concept rather than one spelling of it. The collapsed token is then weighted as the two words it replaced — otherwise it shrinks both sides of the overlap fraction and quietly raises the bar (3/4 passes the 0.70 floor; the same match after a collapse is 2/3 and fails).

Order matters inside the collapse, and not for the reason you would guess: "cage free" and "free range" share the word free, so whichever runs first eats it. "Cage Free Range Eggs" is a real label, and the three-word rule runs first to hand both concepts their own token — otherwise a "free range eggs" request vetoes the very product it was looking for.

What was measured and deliberately left alone

The same defect shape exists on families that are not in the critical set at all — "glutenfree white sandwich bread" vs "White Sandwich Bread" scores 75, as do fat-free and dairy-free variants. Those score 75, not 100, so nothing auto-adds: it is a wrong suggestion, not a wrong add. Adding them means introducing new veto concepts rather than reconciling spellings of existing ones, which changes matching broadly and wants its own measurement. Filed as MEAL-168.

sodium is deliberately not extended either: it is a single word that works as a single word, and a lowsodium concept would newly veto "Reduced Sodium" against a "low sodium" request — a real behaviour change, not a spelling fix.
