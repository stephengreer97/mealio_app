Nothing about a draft is derived in the app

Which fields are flagged, what the callout says, and which span of the source it quotes are all decided server-side in lib/import/draft-form.ts and arrive already worded. A second copy of those rules in the mobile repo would drift behind whatever version of the app a creator happens to have installed — and the two would then disagree about which fields we verified. The same reasoning governs the links card's notices and importPaused: importPaused is the fact stated as a fact, so the screen can stop claiming a link is being polled without matching a string against prose.

Design rules the queue is built on

RuleWhy
Position is shown — "3 of 10"an unbounded stack of cards is what people force-quit
Cursor persisted as an id"backgrounded" and "the OS killed it while backgrounded" are the same thing from here; an index survives neither correctly
Skip is first-classotherwise the only way to leave an uncertain draft is to decide it — and the decision made under that pressure is Approve
A view in the tab, not a modalthe tab bar stays up, so a creator who came to fill a cart is one tap from Discover at every moment, including one who arrived from a notification
Exceptions onlya verified field is simply shown; the summary line is what tells the creator that silence means checked, not skipped
No "approve all" — anywherebulk-approving unreviewed extractions is precisely what the per-field checks exist to prevent, so the button does not exist and the server refuses a batched approve as well
Counts, never a confidence scorea "92% confident" badge is the anti-pattern

Read and write are not the same permission

A YouTube connection lets Mealio read a channel — titles, descriptions, and captions for a video whose description is thin. The switch beside it is consent to write: to append the Mealio link to a video's description once a recipe from that video is live. MEAL-77 forbids conflating them, so the switch is separate, off unless turned on, and revocable in one tap.

For a creator with no channel the card renders nothing — hidden, not disabled. A permission prompt about a channel that does not exist is one a creator learns to tap past, which is exactly what makes the next one worthless. Adding a channel link in the links card above makes the card appear.

Connecting leaves the app and disconnecting does not, and that asymmetry is forced: Google refuses its consent screen in an embedded WebView, and /api/creator/youtube/callback redirects to mealio.co/creator with no deep link back. An in-app attempt would strand the creator on a web page half way through. Disconnecting is one authenticated DELETE with no redirect — and it is revocation, which should never be the harder direction.

The append consent is enforced by assertAppendAllowed on the server. Nothing on this card is the enforcement.
