The H-E-B network switches (MEAL-200, MEAL-202)

Three keys that only mean something together: cartSkuConfirm supplies the transport, networkAdd writes with it, and networkSearch reads with it. All three off by default.

{"stores":{"heb":{"cartSkuConfirm":true,"networkAdd":true,"networkSearch":true}}}

Pushing networkSearch alone does nothing, and pushing it with networkAdd off would be worse than either path alone — no page load for the search, then one per item to click the add. The engine requires all three before it takes the route, so a partial push degrades to the pooled path rather than to something slower.

An older client that does not know these keys drops them with a warning and runs its bundled defaults, which is what makes them safe to push without gating on an app version.

The exact rejection pattern

A selector or URL is refused if it matches /['"\\`\r\n\u2028\u2029<>]|\${/ — a quote, a backslash, a backtick, a newline or carriage return, a Unicode line or paragraph separator, an angle bracket, or a template substitution opener. Every one of those is a way out of the JavaScript string literal the value gets interpolated into. URLs additionally have to be absolute https and at most 500 characters; selectors at most 500.

Two rules that make a config safe to push without gating on app version

  1. The payload is partial. It carries only the keys that differ from what the binary ships, so an empty {} is valid and means "the bundled table is fine".
  2. Unknown keys are ignored, and every known key is type-checked and bounded. A malformed push degrades to the bundled default for that one field — it can never brick the engine.

Selectors must be read inside a build function

The remote config arrives after the store-script modules are imported. A module-scope capture would freeze whatever the bundled default was at import time and a config push could never turn it on — so every script constant carrying a selector is a function, not a template-literal const. That is why adapters are built per call rather than once: a push takes effect on the next cart run instead of requiring an app restart.

Why two identical pipelines instead of one

The automation config and the store catalog answer different questions — how to drive a store, and which stores exist — but they have the same failure modes, so they have the same shape down to the clause. Neither imports its own persistence: ./store pulls in expo-secure-store, which the pure-node test project cannot transform, and every store script imports the config to read selectors. Persistence is injected instead, wired in App.tsx and faked in tests. The catalog keeps React out for the same reason; its hook lives in ./useStores.

Kill switches, and what they take down

SwitchScope
stores.<id>.enabled: falseone store — getStoreScripts returns null and the store surfaces the normal "unavailable" UI
stores.albertsons.enabled: falseall 15 Albertsons banners — they share one config key

A push naming one is refused with a warning rather than silently accepted — a switch wired to nothing reads like something an operator can pull in an incident. Per-store networkSearch / networkAdd / cartSkuConfirm are what turn a rail off without a release.
telemetry.sampleRatereporting cost, without a release

Only selectors live in the platform table. URLs, kill switches and worker knobs stay per-store deliberately: a switch that took down 15 brands at once would be a worse tool than one that takes down the banner that broke.

A re-platforming push is bounded, not dangerous

Adapters keep their full compiled-in fallback set, so the worst a wrong platform value can do is drop the store back to the selectors that shipped in the binary.
