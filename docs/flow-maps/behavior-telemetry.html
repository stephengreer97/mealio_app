Did the user get their groceries?

Read off lib/north-star.ts and lib/automation-telemetry.ts. "The automation ran" and "the user got their groceries" are different numbers, and only the second one is worth steering by.

2026-09-04. A blocked row with reason: 'no_store' codes as auth_required, not waf_block. It is a session precondition — the user has never told the store which branch they shop at — and charting it as a robot wall would say a WAF got harder when what happened is that somebody opened the app for the first time.

Two reasons the network rails added (MEAL-200, MEAL-202)

  • search_unanswered → match_rejected. The network search could not answer for a term — the wall, a timeout, a shape we did not expect. NOT "the store has nothing", which comes back as an ordinary empty candidate list. The item goes to review, so nothing was attempted and nothing needed confirming.
  • write_unresolved → confirm_failed. A network write whose answer was lost AND whose cart could not be re-read. The run deliberately does not click in that state — clicking on top of a write that did apply adds the item twice — so there is no evidence either way.
  • quantity_limit_reached → out_of_stock. The store's own per-item cap is already met by what the cart holds, so there is nothing this run can add. Not a confirmation failure (nothing was attempted) and not a scoring one (the product matched exactly) — the store is declining on stock policy.
  • unexpected_shape → confirm_failed. The store answered and the answer was not a shape we know: the contract moved, or a field we depend on is gone.

The guard was disarmed for this rail, and the test went on passing. It finds reasons by scanning for a lowercase word-boundary "reason", and the network add passed its reasons POSITIONALLY — so fifteen were invisible, seven of them with no code at all, riding the unmapped default. Naming them exposed the seven. An uppercase constant did not work either. Anything new in these scripts has to be written where the scanner can see it.

error_arm is mapped too, and is deliberately unreachable today: the guard requires a code for every reason the scripts can emit, and that one only ever reaches a debug line because the run falls back to clicking and reports whatever the click did.

The one debatable call, taken conservatively

A skipped-in-review item stays in the denominator. Review is only ever reached because the automation failed to match the item on its own, so a skip is a user giving up on our miss more often than it is a change of mind. We cannot tell the two apart, so the number takes the reading that never flatters us — and skippedInReview ships alongside so the read side can compute the other one.

The one code that makes a store look better

out_of_stock is the only failure code that names no fix family, because there is no fix: the store is out of the item. It exists so that outcome stops being counted as one of ours — before it, that case rode match_rejected, which put the store's inventory on the same bar as our scoring being wrong.

It is also the only code that improves a store's numbers: the server subtracts these items from the item-success denominator, so a store reporting more of them reports a higher success rate. That puts real weight on the store scripts being right about which items get it.

Codes are appended, never renamed or removed

The code is stored as a raw string on every row ever written, so a rename splits a metric's history and a removal orphans the rows already carrying it — neither of which fails anywhere visible. Nothing reads the order of the code list; what is order-sensitive is FAILURE_CODE_SEVERITY, which is a separate list for exactly that reason.

This list used to be described as a contract shared with the Kroger Brands web extension, needing agreement on both sides before a code could be added — which had become a standing block on work. That is no longer true: the extensions are retired, the Kroger Brands integration writes no automation_steps rows at all, and the ingest route stores the string as-is without checking it against any enum. This app is the only producer, so appending is a one-repo change.
