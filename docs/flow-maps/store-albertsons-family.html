Albertsons family — 15 banners, one platform

Safeway, Vons, Jewel-Osco, Shaw's, Acme, Tom Thumb, Randalls, Pavilions, Star Market, Haggen, Carrs, Kings, Balducci's, United — and Albertsons itself. Read off webview-scripts/albertsons.ts. One selector table, one kill switch, one cart path; only the host differs.

2026-09-04. The DOM half of this store is gone: the selector table, the 511-line login check that read the account menu's rendered name, and the selector-drift instrumentation (selector-health.ts) that watched them. The rail's session probe is the only answer to "who is signed in" now, and there is nothing behind it to fall back to — a session that cannot answer asks the SITE to fix itself (one load of the real storefront) rather than reading a page for a second opinion. The rail itself moved from network-rail.ts into albertsons-network.ts.

2026-09-04 — the unavailable line is undone. This platform accepts a write for an out-of-stock product and flags the line isAvailable: false; the rail refused to claim the add but the line stayed in the cart. It is now taken back out in one follow-up POST to the same batch endpoint, restored to the quantity held before the run. UNMEASURED, and the code is built for it: whether qty: 0 truly removes a line here has not been proven against the live store (the device session had expired), so the response's own cart is read and the user is told plainly if the store would not let go.

2026-09-04 — Amazon Fresh is gone. It was the last store with no network rail, so it could only search and hand the user the page to add from. Removed from the catalogue rather than carried as the one store Mealio cannot add to. Every store here now has a rail; the last DOM read in production went with it, and "assisted" is now a state a store passes through (rail off, or unable to answer) rather than what a store IS.

One config entry for fifteen stores

All 15 banners read the shared albertsons key. The adapter passes that fixed key to selectorsFor() and storeConfig(), and getStoreScripts checks the kill switch against it, so enabled: false stops the whole family — deliberately. A switch that took down 15 brands at once would be a worse tool than one that takes down the banner that broke, which is why only selectors live in the platform table and URLs, kill switches and worker knobs stay per-store elsewhere. Here the URLs are derived from the storeId instead: a per-banner URL override would need 15 entries to say one thing.

Two host mistakes that cost real runs

United is shopunitedsupermarkets.com, not unitedsupermarkets.com (MEAL-136). The latter is the banner's Squarespace marketing site: it 301s to the shop host discarding the path, which then 301s to www. Every URL built for that banner — /erums/cart, /shop/search-results.html — landed on a marketing home page. No cart, no product tiles, nothing that failed loudly. A path-discarding redirect is invisible at runtime, so url-builders.test.ts pins it.

The cart is /erums/cart, not /shop/cart.html (MEAL-151). The old path 404s. cartUrl has exactly one consumer — the Linking.openURL that opens the user's cart in the real app — so every tap of that button landed on a 404 page. The path is written once, as ALBERTSONS_CART_PATH, because two copies of a path is how one goes stale without the other noticing.

Search the first five words, match the full name

Albertsons over-constrains on long queries — a full product title, especially with its size suffix, returns zero results. albertsonsSearchQuery sends the first five words only; the matcher still compares candidates against the complete saved name, so precision is not traded away for recall.

Why the login check is this elaborate

The storefront bounces through an SSO authorize URL and straight back, ~5 s, and both injection sites re-inject on every page load. Defence 1 (bail on the interstitial) is the one that saves the time; defences 2 and 3 stop a wrong or duplicated verdict.

The cache is a tiebreaker, not a fast path. As an unconditional fast path a cached 'in' outlived session expiry forever: the header plainly read "Sign In" and the cache still answered true. SilentLoginProbe latches so it never asked again; WebViewCartSheet waited for a LOGIN_STATUS:false that could not arrive; every add then failed silently against a signed-out session. Live detection now always wins when it can see the header, and a negative verdict clears the cached positive. That ordering costs ~20–30 ms against a ~1 ms cache read. Wegmans carries the identical shape — change the two together.

The empty-span bug, twice. The passive rule's regex (account menu) matches static markup present in both auth states, so the entire verdict rests on the conjunct in front of it. MEAL-124 made that conjunct "the name is non-empty" — but a skeleton placeholder ("…", a spinner glyph, "Loading") satisfied "non-empty" and read as a signed-in user just as an empty span had. MEAL-140 raised the standard to acctTextResolved: text that has settled — letters, not a loading word. An unsettled span now spends the full budget and takes the click-check path, which resolves to signed out — the direction that shows a login wall rather than failing every add in silence. The three ambiguous outcomes are logged under three distinct labels on purpose: a log that conflates them cannot tell a thin rule from a moved header.

The session token that is deliberately not used

MEAL-15 found the session bearer on a page global — window.AB.userInfo.SWY_SHOP_TOKEN, which Albertsons' own chat widget labels okta_token — and proposed it as the passive login marker. It reads strictly better than a markup heuristic: a positive fact about the session rather than an inference from DOM that exists in both states. It is still not wired in:

  1. It would not fix the bug. The property is populated by the Angular bootstrap at runtime, so pre-hydration it is simply absent — exactly the window MEAL-124 is about. Absent has to fall back to the DOM heuristic (nothing fixed) or to signed-out (a login wall for every signed-in user we inject early). It moves the race; it does not remove it.
  2. What matters is still unobserved. MEAL-137 confirmed the property is non-empty on a settled signed-in tab, and that an in-page fetch carrying it reached the cart service's application layer. Unobserved: its value during hydration, what a guest holds, the format of tokenExpiration — and none of it inside our WebView, the only place this code runs. The token lives 45 minutes, so "present" and "usable" are not the same property.
  3. It is unexercisable here. Fixture tests load static HTML with scripts blocked, so window.AB never exists; the token path would ship with no coverage while the covered path went unused.

So it is recorded as a presence-only diagnostic (never the value — it is a live bearer) in the passive_decision payload, so the missing observation can come off a device log instead of a hand-run DevTools probe. Promoting it later means making it a cross-check that must agree, never a signal that can decide alone. tests/fixture-tests/albertsons.spec.ts pins the refusal.

Worker count is a memory limit, not just an anti-bot one

3 workers staggered 400 ms. Five concurrent WebViews crashed the iOS WKWebView content process on its shared memory budget; three also happens to match the low global default for anti-bot reasons. Unlike ALDI and Wegmans the parallel path stays on — and both knobs are remotely tunable, so a new WAF can be answered with a config push.
