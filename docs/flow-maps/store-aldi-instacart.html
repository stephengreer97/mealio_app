ALDI — and the Instacart Storefront platform

ALDI HAS A RAIL (2026-09-03)

MEAL-211 asked whether this store could have a real rail like H-E-B and the Albertsons family. It can, and it does. Every operation was executed against a live signed-in session before a line was written — see docs/network-rail-research/02-aldi.md.

Registered against the PLATFORM, not the banner. getNetworkRail never names ALDI; it asks isInstacartStore. A tenant added to INSTACART_TENANTS gets this rail with no second entry — the same reasoning that gives fifteen Albertsons banners one rail.

Persisted queries only. A query sent with its text is refused (PersistedQueryNotSupported), and so is introspection. The rail harvests the operation→hash map out of the storefront's own JavaScript, caches it 12 h, and forgets the cache on PERSISTED_QUERY_NOT_FOUND — the Albertsons APIM-key pattern, including its forget-on-rejection trigger.

The add is OFF, and not out of caution. Nobody has measured whether this store SETS a cart line or ADDS to it. The script therefore writes only where the two readings agree — the cart holds none of the item, so held + wanted is just wanted — and DECLINES an item the cart already holds, with a reason that reaches the review screen. Two fixture tests run the same script against a stub that sets and a stub that adds; the cart is correct under both. Measure the semantics, set absoluteQty, flip networkAdd.

Everything below about extractors, add clicks, worker pools and selector drift is HISTORY, kept as the evidence that led here. The login check and the search URL are still what the ASSISTED route uses when the rail is off or cannot answer.

One adapter, many banners — but only one has ever run

Instacart white-labels one storefront to many grocery banners, so this module is the platform's adapter, parameterized by an InstacartTenant (origin, slug, cookie domain, and the login word lists, which is where banners diverge most). It began as aldi.ts when ALDI moved onto the platform in its Q1 2026 relaunch and was generalised in place, so every injected script is the exact text that drove ALDI before the extraction.

ALDI is the only tenant in INSTACART_TENANTS, and the only banner we hold captured HTML for. MEAL-20 records that aldi.us, delivery.publix.com and shop.sprouts.com all return 200 for the same /store/{slug}/s?k= route — but a matching URL contract is not a matching DOM. Treat every selector here as the platform's likely shape, not its confirmed one.

cardLink cannot move up into the platform table — it weaves in the tenant's own /store/{slug}/ path, and the platform table is static JSON that does not know which tenant is reading it. Slug-parameterised selectors stay at the floor.

What is unique to ALDI

Every runtime knob here is an anti-bot concession. forceSerialSearch: true, cacheBustNav: false, workerCount: 3, workerStaggerMs: 400 — the worker path is built and kept so a config push can re-enable it without a release, but it is not reached. Concurrency itself is the trigger, not the cache-buster.

No cart page and no login page. The cart is a side panel and login is inside the hamburger menu, so cartUrl and loginUrl both fall back to the banner origin. isSearchUrl returns true for any /store/ URL, because the search bar is available on every store page — which skips a storefront reload and injects search directly.

spaSearch: true. Search is a pushState route change, so the same page fires onLoadEnd repeatedly while the add script is still running. Suppressing inflight re-injection is what stops a double-add and a skipped item.

Cart probing comes free. buildInlineCartScript() and extractorFor() in cart-count.ts dispatch on isInstacartStore(), not on the string 'aldi' — which they used to, giving any second banner no cart probe at all.

The inline scorer that no longer decides anything

buildSearchAndAddScript carries its own scoreOne/scoreMatch that has drifted from _scoring.ts: a 0.3 overlap floor instead of 0.7, a ±15 critical-word penalty instead of a hard veto, −5 per extra candidate word, and a stopword set with no counterpart. Over 469 real pairs the two disagree on 427.

None of that decides a purchase any more. It used to gate the add — keep the top scorer, buy it above 30/100 — so a name sharing under a third of its words with the request could go into a cart unattended. isExactMatch gates the add now, exact after normalization like every other store, and the two functions are unreachable from the decision path. Deleting them would touch the generated-script snapshot and nothing else.

If anyone does reconcile them: the argument order is inverted. This scoreOne(nf, nt) reads its second parameter as the query; _scoring.ts's scoreMatch(a, b) scores candidate b against term a. A naive substitution silently flips the comparison and still returns plausible numbers, so nothing fails loudly.
