Amazon Fresh add-to-cart automation

Amazon Fresh is ASSISTED (2026-09-01)

DOM automation was removed from Mealio. Amazon Fresh had no API or in-page rail behind it, so it no longer adds to the cart on the user's behalf: Mealio searches each ingredient and hands the user the results page; they add what they want and tap Next.

Everything below about extractors, add clicks, worker pools and selector drift is HISTORY. It is kept because it is the evidence for MEAL-212, which asks whether this store can have a real in-page rail like H-E-B and the Albertsons family — and because the login check and the search URL, which the assisted route still uses, are described here too.

2026-09-04. The selector table (SEL_FALLBACKS) and the badge-confirmation module cart-confirm.ts are gone; nothing had called either since the DOM scripts went. This store's cart-page reader moved here too, off a shared table in cart-count.ts and onto StoreScripts.cartPage in amazon-fresh.ts. Amazon Fresh is now the ONLY store in the build that reads a storefront at all — its login check — and that check is primary, not a fallback, because this store has no rail to fall back from.

Read off webview-scripts/amazon-fresh.ts, which now holds everything this store does. The only store where the page can be perfectly healthy and still return nothing — because the account has no Fresh store selected.

What is unique to Amazon Fresh

Two card layouts, not one. The storefront carousel (Type A) and search results (Type B) are different components with different add controls, different steppers and different quantity readouts. Almost every selector in SEL_FALLBACKS comes as an A/B pair, and the add path forks on bestCard.matches(CARD_B). Both are lazily rendered, so both poll.

Zero results can mean "your account has no store". When the Amazon account has no Fresh store or serviceable delivery address selected, every search returns Fresh's own empty state. Counting products would report that as a per-item miss for every ingredient in the meal. __freshEmptyState() matches the distinct phrasing instead — which also means a broken card selector cannot be mistaken for "no store", because zero cards alone never triggers it. The flag rides back as storeUnavailable so the app can say the real thing.

A click may open a sheet rather than add. Weight- and quantity-selected items intercept the add with a "Select quantity" modal. confirmWeightModal first checks whether the quantity simply advanced (no modal at all), and only then hunts for the sheet three ways, in descending specificity. Strategy 3 explicitly excludes controls inside the source card — those are the + buttons already clicked.

Re-adding an item already in the cart skips the add button entirely. On Type B that button opens a modal whose quantity selector is pre-set to what the cart already holds, so committing it changes nothing. The loop starts at 0 instead of 1 and goes straight to increments — otherwise the first requested unit is silently lost.

The badge is the only confirmation this store has. buildCartConfirmFn is imported only here. H-E-B has a real per-product cart query in front of its badge; Amazon Fresh has the counter and nothing else, so success is "the header count went up within ~10 s". An unreadable badge deliberately resolves to success after a 2.5 s settle rather than failing — a markup change must not turn every add into a reported failure.

Cart deep link. appScheme is com.amazon.mobile.shopping.web://amazon.com/gp/cart/view.html — the URL-carrying scheme. Bare amazon:// and amzn:// do not work.
