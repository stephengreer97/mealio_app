2 · How a run is shaped

DOM automation was deleted on 2026-09-01. Nothing clicks a storefront any more. There were five routes through this table — a sequential page walk, a parallel search pool, a fused search-and-add pool, a pre-search parking pool, and the network rail. Four of them worked by driving hidden WebViews through the store and pressing its buttons, and they were the source of most of what went wrong: selectors that went stale, clicks that raced the page's own navigation, adds that reported success and never landed.

Three routes are left, and none of them clicks.

RouteWho gets itWhat it does
networkH-E-B, Albertsons family Search and add by asking the store's own API from a signed-in WebView. No page loads at all — including the cart reads, which the rail answers itself (NetworkRail.cartRead). Verifiable: every write is checked against that write's own response.
networkChoosethe same two, on a choose run The same rail, SEARCH ONLY. A choose run needs candidates for the Choose Products screen, not adds. It asks, it does not buy.
assistedWalmart, ALDI, Amazon Fresh, Wegmans Mealio searches each ingredient and hands the user the results page; the user adds and taps Next. No automation, and nothing claimed that was not seen. It is what “manual mode” already did, promoted from a rescue to a route.
—Kroger family Never reaches this decision: the SERVER fans out per ingredient.

The four assisted stores had no other rail, so removing DOM automation is what put them there. MEAL-210–213 ask, one per store, whether each can have a real in-page rail like the two that do — each citing what is already ruled out, so nobody re-runs MEAL-17 (Walmart affiliate URL, blocked), MEAL-18 (Amazon cart URL, dead) or MEAL-34 (Instacart platform, not a path).

The rail assumes one document, and does not always get one. Its batch runs inside the page it was injected into; if that page navigates mid-batch every in-flight fetch rejects as TypeError: Failed to fetch and the loop stops dead. An 18-term run died at 3/18 that way — three failures, then silence, no SEARCH_BATCH_DONE. Three failures and SILENCE is the tell that separates it from a bot defence, which would have refused all 18. onLoadEnd during the search phase re-asks the terms that never came back, capped at three documents.

Albertsons is fifteen banners sharing one config entry, stored under albertsons. The cart engine used to look its rail flags up by the LOCKED STORE ID, so Safeway read stores['safeway'], found nothing, and was treated as a store with no rail — a silent downgrade for fourteen stores, invisible because every Albertsons run measured had been on the banner literally named albertsons. railConfigKey() is the one place that mapping lives now.

Albertsons family		 The rail's session probe, always. H-E-B asks myPreferredStore over GraphQL; Albertsons reads its Angular bootstrap and the cart service. It answers all THREE places that decide login — the silent prewarm, the login_check step, and the re-ask on every page load while the user sits on login — plus a poll on that step, because the page-load re-ask is gated on isLoginSuccessUrl/reinjectLoginCheckOnNav and a store with neither used to need the user to press "I'm already logged in". One second, one question at a time, five seconds after the first thirty: it is a REQUEST to the store (two GraphQL posts at H-E-B, a 455 ms fetch at Albertsons), not a page read. The DOM check is the fallback, reached only when the probe cannot answer, which is nearly always a page that has not finished its bootstrap — NOT a signed-out user, and it must never be reported as one.

How many answers it gives is a STORE fact (rail.sessionUsable). H-E-B posts once. Albertsons posts TWICE: an early one the moment /userinfo replies — so no budget of ours can make the sheet think a signed-in user is signed out — and a refined one ~1.3 s later once the API keys are resolved and the token is proved against a real cart read. Only the refined one can search or write. The engine had "a session probe answers once" baked in and took the first: measured 2026-09-02 as wrote 0 of 29 and twenty-nine 401s, because the subscription key the write reads is a page global that only the refined answer's cart read sets. Asked in THREE places, all of which had it wrong: the run's session phase, the search prewarm, and the login_check branch that starts the run. 5 · Defaults, and where they actually come from

This table used to size the worker pools — how many parallel search workers, how many add workers, the dispatch stagger, the commit jitter, the add-worker timeout. All of it existed to pace concurrent WebViews through a storefront without tripping its bot defence, and all of it went with them.

KnobEffective defaultSet in
rail search concurrency3 (H-E-B), 2 (Albertsons) the rail's own batch script. Albertsons is lower because MEAL-207 has its search degrading under load, and it opens with ONE request before the lanes fan out
rail add concurrency2, capped at 3 addBatch(items, { concurrency })
search deadline40 s, re-armed per document netArm — a navigation mid-batch buys a fresh window
write deadline75 s first pass, 45 s top-up netArmFinalize. When it fires it finalizes with what came back rather than starting a second pass
cacheBustNavonper store; off only for ALDI and Wegmans. Still real: an assisted run navigates

The remote flags are gone too. FlagConfig held four — parallelAdd, presearchAdd, parallelAddWorkers, addCommitJitterMs — and every one was a lever over the pools. A switch wired to nothing is worse than no switch: it reads like something an operator can pull in an incident. The section is empty and a push naming any of them is REFUSED with a warning.

What stayed remote is the part that still decides something: networkSearch, networkAdd and cartSkuConfirm per store, which is how a rail is turned off without a release.

What is deliberately not remote

Everything in tables 2–4 is remotely tunable. Nothing in table 1 is. KROGER_BRAND_IDS and WEBVIEW_STORE_IDS assert that this binary contains code for a store, and no server response can make that true — a database row would otherwise promise automation the installed app cannot deliver. The catalog can add a store's name; only a release can add its automation.
