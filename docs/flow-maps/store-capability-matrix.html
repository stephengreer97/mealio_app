Store capability matrix

Every value below is read from the code, not from the docs — the adapters, automation-config/schema.ts, webview-scripts/cart-count.ts and the defaults in WebViewCartSheet.tsx. Where a comment and the code disagree, the code is what is listed and the disagreement is named at the bottom.

No DOM login check anywhere a rail exists (2026-09-04)

Every rail store's page-reading login check is deleted, and nothing falls back to one: a store with two ways to answer "who is signed in" has no way to tell you which answer you got. A session that cannot answer now asks the SITE — one load of the real storefront, then the same probe again on that page, for up to 30s — and only hands the user a sign-in screen if that fails. Amazon Fresh is the exception and the only one: it has no rail, so its check is primary rather than a fallback.

2026-09-04. Two engine-wide fixes found by driving the Pixel: the sheet's open now navigates rather than re-writing the same URL (a re-open fired no load event at all, and every rail phase waits on one), and a review screen opens on the first candidate that is actually in stock. Both affect every store equally — neither is a store's own behaviour.

2026-09-04 — no rail store could show its sign-in page. The login step skipped its navigation whenever the WebView was "on the store's domain", and a rail parks on robots.txt, which is. H-E-B, the fifteen Albertsons banners, ALDI, Wegmans and Walmart all presented a blank page under "Log in". Fixed in lib/login-page.ts; see the cart-engine map.

2026-09-04. The over-add warning no longer blames the user for a line the STORE created: an item whose write was accepted and flagged unavailable used to be reported as "Mealio didn't intend to add". See the reconcile map.

2026-09-04 — unavailable is out of stock, everywhere

H-E-B refuses the write and says why. The mutation had always selected the error code and nothing read it, so an out-of-stock refusal was filed as a generic error_arm — not a definitive failure, so it went to RETRY, hit the same wall, and was reported as unaddable with no review card. It now reports out_of_stock, which routes to review with alternatives.

Albertsons does the opposite: it ACCEPTS the write and flags the line unavailable. Refusing to claim the add left a real line in the basket, so the user was picking a substitute for something they already had. The write now undoes those lines in one follow-up request, back to the quantity the cart held BEFORE the run — never blindly to zero, so a line the user already had is restored to theirs.

Both end in the same place: the ingredient goes to review with candidates, and the cart is left as if the item had never been addable.

2026-09-04. H-E-B's per-product cap now comes from the CART as well as the search (product { maximumOrderQuantity }, which its own CartItemFragment selects) — a run whose products are already chosen skips the search, so those items used to reach the write with no cap and no way to know they were at one. And a signed-out answer from a rail's quiet page is no longer acted on until the storefront has had one load; see the cart-engine map.

2026-09-04 — Albertsons removal, measured. A quantity of 0 does NOT remove a line here: it answers 400 and the line stays. The removal is DELETE /cart/items taking the same body the add takes, with the user's real serviceType (DUG) — every 400 along the way was that one parameter. A line the run CREATED is deleted; a line the user already had is set back to their quantity.

2 · How a run is shaped

DOM automation was deleted on 2026-09-01. Nothing clicks a storefront any more. There were five routes through this table — a sequential page walk, a parallel search pool, a fused search-and-add pool, a pre-search parking pool, and the network rail. Four of them worked by driving hidden WebViews through the store and pressing its buttons, and they were the source of most of what went wrong: selectors that went stale, clicks that raced the page's own navigation, adds that reported success and never landed.

Three routes are left, and none of them clicks.

MEAL-210–213 ask, one per store, whether each can have a real in-page rail like the two that do — each citing what is already ruled out, so nobody re-runs MEAL-17 (Walmart affiliate URL, blocked), MEAL-18 (Amazon cart URL, dead) or MEAL-34 (Instacart platform, not a path).

The rail assumes one document, and does not always get one. Its batch runs inside the page it was injected into; if that page navigates mid-batch every in-flight fetch rejects as TypeError: Failed to fetch and the loop stops dead. An 18-term run died at 3/18 that way — three failures, then silence, no SEARCH_BATCH_DONE. Three failures and SILENCE is the tell that separates it from a bot defence, which would have refused all 18. onLoadEnd during the search phase re-asks the terms that never came back, capped at three documents.

Albertsons is fifteen banners sharing one config entry, stored under albertsons. The cart engine used to look its rail flags up by the LOCKED STORE ID, so Safeway read stores['safeway'], found nothing, and was treated as a store with no rail — a silent downgrade for fourteen stores, invisible because every Albertsons run measured had been on the banner literally named albertsons. railConfigKey() is the one place that mapping lives now.

5 · Defaults, and where they actually come from

This table used to size the worker pools — how many parallel search workers, how many add workers, the dispatch stagger, the commit jitter, the add-worker timeout. All of it existed to pace concurrent WebViews through a storefront without tripping its bot defence, and all of it went with them.

The remote flags are gone too. FlagConfig held four — parallelAdd, presearchAdd, parallelAddWorkers, addCommitJitterMs — and every one was a lever over the pools. A switch wired to nothing is worse than no switch: it reads like something an operator can pull in an incident. The section is empty and a push naming any of them is REFUSED with a warning.

What stayed remote is the part that still decides something: networkSearch, networkAdd and cartSkuConfirm per store, which is how a rail is turned off without a release.

What is deliberately not remote

Everything in tables 2–4 is remotely tunable. Nothing in table 1 is. KROGER_BRAND_IDS and WEBVIEW_STORE_IDS assert that this binary contains code for a store, and no server response can make that true — a database row would otherwise promise automation the installed app cannot deliver. The catalog can add a store's name; only a release can add its automation.
