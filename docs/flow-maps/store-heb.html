Three request parameters do more than the speed does. excludeSponsoredContent means the sponsored and "perfect pairings" tiles are never asked for, so they cannot be mistaken for results — a class of extraction bug that stops existing rather than being fixed. includeOutOfStock replaces reading stock off button text. pageSize states the result count instead of accepting however many tiles rendered.

The per-item cap has to be respected before asking. The write sets an ABSOLUTE quantity, so what the cart already holds plus what was asked for can exceed the store's maximumOrderQuantity — and the store refuses the WHOLE write. Measured: an avocado came back "Quantity limit reached." because earlier runs had already put twenty in the cart. Clamping is right where it still adds something and wrong where it does not, because clamping to a number the cart already holds writes no change and would report success — an under-add dressed as a win.

Purchase preferences travel as the choice already does. The page path clicks a modal row by its LABEL; the network path states a purchasePreferenceId. Both come from the same user choice, so the id is looked up by the label that was chosen rather than asking again. Nothing chosen means the field is OMITTED rather than nulled, which is what the storefront itself does.

The top-up stays on the rail too. The run already matched these products, so a shortfall is a write rather than a search — re-searching would spend ~1.8 s per item rediscovering an id already in hand. It must NOT go back through finishParallelAdd: a top-up is already the reconcile's own correction, so reconciling it again would find a shortfall and top up the top-up. And it never splits one correction across two rails — if any retry item has no id to write, the whole top-up takes the page path.

Once writing starts, falling back to the page path is forbidden. Every earlier phase can hand the run over safely because nothing has been written. This one cannot: the pool re-adds the whole list by clicking, and its loop baselines off the card label — which by then reflects our own writes — so the user ends up with roughly double. The add phase's deadline finalizes with what came back instead, and the cart read settles the rest.

The write is ABSOLUTE, which makes three ordinary things unsafe. Two ingredients resolving to one product would set the line twice and land base + max rather than base + both, so writes are coalesced by product first. A product that already has a line cannot take a preference-carrying write, because lines are keyed by preference and the cart read does not say which line is which. And a product that offers preferences is never written without a confident id — the saved label comes from a DOM modal row while the network's texts come from purchasePreferenceList, so a drift would silently let the store choose the variant.

The store identifier is the trap. me.preferredStore.storeNumber and cartV2.fulfillment.store.id are both store identifiers and they differ — measured 243 and 476 for one shop. Search wants fulfillment's. Sending the other searches a different catalogue and returns results that look entirely reasonable.

Three things the shape is hiding

The before-snapshot is load-bearing. If CART_COUNT phase=before never answers, there is no baseline, so there is no after-probe — and nothing in the run can contradict the workers. Every silent add defect reports success on its own checks; the cart diff is the only thing that has ever disagreed.

Reconcile trusts the cart, not the workers. A worker saying "added" is a claim. reconcileParallelAdd splits those claims three ways against a real cart read: confirmed, retry (re-added serially, unattended), and unverified — the count-item-on-a-weight-row case, which is neither re-added (that buys it twice) nor confirmed (that claims a delivery nobody checked).

A search failure ends as skipped, not failed. No exact match sends the item to the review screen, and the user's Skip there puts it in skippedNames. That is why manual mode offers failed and skipped — offering only the failed ones made the feature unreachable on the run that needed it.

What is unique to H-E-B

  • spaSearch: true — the search route re-renders and fires onLoadEnd a second time for the same URL. Without the flag the engine re-injects, spawning a duplicate SEARCH_AND_ADD_RESULT that over-advances the item index and silently skips an item.
  • nextDataSearch (off) — read results out of <script id="__NEXT_DATA__"> instead of scraping cards, which is where the sponsored and "perfect pairings" carousels simply are not present. Degrades back to the DOM extractor at runtime, so it can lose speed but not correctness.
  • cartSkuConfirm (off) — confirm each add against H-E-B's own cart query instead of the header badge. Every failure mode resolves to "we could not read the cart", never to "the item is missing".
  • networkAdd (off, requires cartSkuConfirm) — diagram 2.
  • networkSearch (off, requires networkAdd + cartSkuConfirm) — ask the store's gateway for results instead of loading a results page. Together the two make a run that never navigates: 10.8 s tap-to-reconcile against 22.5 s, measured on a device over twelve ingredients, with all twelve searches taking 1.0 s. It also runs no worker WebViews, which is about 187 MB of the memory peak. See diagram 3.
  • Two login URLs. A logged-out profile click redirects to accounts.heb.com, an OIDC /authorize URL the generic auth-redirect skip would swallow, so H-E-B declares its own isLoginPageUrl and re-injects the login check when the chain settles back on the store.
