Kroger family — the API path

Kroger, King Soopers, Ralphs, Fred Meyer, Fry's, QFC, Harris Teeter, Mariano's, Smith's, Baker's, Dillons, Pay-Less, Pick 'n Save, Metro Market, City Market. Read off components/KrogerCartReviewSheet.tsx, lib/api.ts and screens/account/AccountScreen.tsx. No WebView, no selectors, nothing for a redesign to break.

2026-09-04 — Amazon Fresh is gone. It was the last store with no network rail, so it could only search and hand the user the page to add from. Removed from the catalogue rather than carried as the one store Mealio cannot add to. Every store here now has a rail; the last DOM read in production went with it, and "assisted" is now a state a store passes through (rail off, or unable to answer) rather than what a store IS.

Why this store family has no selectors

The Kroger family runs on Kroger's public API, not on DOM automation. That is why PlatformId declares a 'kroger' platform with no selector table and never will need one: there is nothing for a storefront redesign to break, no anti-bot to negotiate with, no login heuristic. It is declared at all so a Kroger store's platform field can say what it actually is rather than being mislabelled 'standalone'.

Everything else in the app treats it as a peer: isCartEnabled = isKroger || isWebView, the same multi-select on the meal cards, the same "Choose products once to add this to your cart" warning, the same lastAutomationRun bookkeeping.

Three things worth knowing

Two match tiers, and only one auto-adds. The server returns exact per ingredient. Exact results go straight into the cart payload; everything else goes to the review queue with a reason the sheet renders in the user's words. That is the same cart governing principle as the WebView stores, arrived at server-side instead of in an injected script.

A custom search never auto-adds. Even if the term the user typed scores exact, resolveCurrentSelection shows the suggestion list. The user typed a term in order to choose; silently adding would take that back.

"Update" is the one action that changes the meal. Picking a substitute and choosing Update writes searchTerm (and the per-meal quantity) back onto every meal that used that ingredient, so the next run matches exactly and skips the review entirely.

The chosen product is remembered by identifier, not by name (MEAL-19)

searchTerm is what a product is called — "Kroger Whole Milk, 1 gal". Storing only that meant every later run searched the name back into a product, so Kroger's relevance ranking re-decided a choice the user had already made. Update and the meal editor's product chooser now write storeProducts alongside it: the UPC Kroger itself handed us, keyed by rail rather than by banner, so a meal moved from Kroger to Ralphs keeps its choices. The server resolves the whole run's ids in one filter.productId request before it searches anything.

It is an accelerator, not a replacement. An id this store will not fulfil, has out of stock, or no longer knows falls through to exactly the text ladder that ran before it existed. A stale id therefore costs a request, never a wrong product.

Keyed per store, and it dies with the choice. Both rules exist for the same reason. searchTerm is one global field and a meal's store can change, so an H-E-B-chosen name already reaches Kroger's search — harmless, because the ladder recovers. An identifier does not need recovering: it resolves, and a resolved id comes back exact, so the review step that would have shown the mistake never runs. So it is never a bare upc field, and the rule at every writer is the name and the id move together or the id goes: renaming the ingredient, retyping or clearing the product-name box, the ✕, and choosing a product at a different store all drop it. A stale weight biases an add; a stale id adds the wrong product outright.

An invariant hiding in a type

ConsolidatedIngredient here carries no weight fields, and that is load-bearing rather than incidental. isZeroedOut's sold-by-weight exception keys off purchaseWeight; with no such key the exception is unreachable and the predicate reduces to the plain productQty > 0 filter Kroger ran before MEAL-65 — which is what makes add-to-cart provably unchanged on this surface. Add a weight field and rows would start surviving quantity 0. Both the type and its builder are exported so qtyStepExclusion.test.ts pins the invariant rather than leaving it to a comment.

Counting

totalAdded is the sum of quantities, not the number of lines (MEAL-178). "N items added to your cart" has to mean the same thing here as on every other store, and this API hands us the quantities outright. Nothing on this path is sold by weight — the REST cart takes a discrete quantity per UPC.

Endpoints

CallPurpose
GET /api/kroger/statusconnected? plus the saved location per storeId
POST /api/kroger/connectreturns the OAuth redirect URL
POST /api/kroger/disconnectdrops the connection
GET /api/kroger/locations?term=ZIP → nearby stores, each with its banner storeId
POST /api/kroger/set-locationpins a locationId to a banner
POST /api/kroger/search-productsingredients (with any saved upc) → upc / exact / suggestions (60 s)
POST /api/kroger/add-to-cart{upc, quantity}[] → the real cart (60 s)
