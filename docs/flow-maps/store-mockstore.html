What the mock store exists to prove

Nine green unit tests can describe a feature no user can reach. The mock store is the answer to that: a real remote https site, loaded in a real WebView, driven by the real registry through the real orchestration. What it removes is only the parts that are not ours — anti-bot, hydration races, markup drift.

The DOM contract

ElementMeans
body[data-logged-in]login state, read synchronously
.mock-product[data-name][data-price][data-oos]a search-result tile
button[data-qe="add"][data-name][data-failadd]its add button — data-failadd makes the add silently not commit
#mock-cart-countthe header badge total
.mock-cart-line[data-name] .mock-cart-qtya cart line on /cart
.mock-no-resultsan explicit empty state, so a zero-card poll ends early

data-oos and data-failadd are the point: they let a test produce the two failures that are hardest to reproduce against a real store — an out-of-stock exact match, and an add that reports success at the button while the cart never moves.

Three deliberate details

It is not probed for selector health. getStoreScripts passes null as its surface: a deterministic fixture store has no drift to catch, and it has no automation-config selector table to sample against.

It lives in WEBVIEW_STORE_IDS unconditionally — selectorHealth derives its coverage from that set and must keep seeing it — so isSupportedStore special-cases the id against MOCK_STORE_ENABLED. Without that line, a remote catalog row named mockstore would surface the dev store in a production build.

The URL hash is how one script serves every item. In worker mode the term and quantity ride in #mealio=<json>, which the server never sees. That is the same mechanism the real stores' parallel-add workers use, so exercising it here exercises it there.

Point it anywhere. EXPO_PUBLIC_MOCK_STORE_URL overrides the deployment, so a local mock server can stand in for the Vercel one.
