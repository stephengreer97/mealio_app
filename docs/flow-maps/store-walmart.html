Walmart add-to-cart automation

Walmart is ASSISTED (2026-09-01)

Walmart has a rail as of 2026-09-03, and it is the fourth. Measured end to end against a signed-in session and then driven through the app: login, search, add, cart read, reconcile — wrote 3 of 3, confirmed 3.

The search is the PAGE, and the page is JSON. Walmart server-renders its results into __NEXT_DATA__, so a search is one GET and one JSON.parse: no rendering, no selectors, nothing to drift. A different shape from the other three rails, which call an API, but the same properties.

⚠ Anchor on the TAG, not the id. An inline script near the top of the document reads getElementById("__NEXT_DATA__"), so a plain indexOf for the id lands ~900 bytes short of the payload and parses minified JavaScript. The first device run reported unparseable on a document that was perfectly fine.

⚠ THE HEADERS ARE THE GATE. content-type alone is answered 418 Access Denied; a partial set gets 429 and a savings interstitial; the full set gets 200. x-o-platform-version must be PRESENT but not correct — a deliberately bogus version still answered 200 — so nothing has to be harvested from a page first. 418/429/403 are reported as blocked, which is not the same fact as an empty shelf.

⚠ An existing line is addressed by lineItemId, and then quantity is ABSOLUTE (measured 1 → 2). Without it the write creates a line and does nothing to one that exists. The field name is load-bearing: plain id and cartLineId both answered "400: Bad Request". So held + wanted for a line that exists, wanted for a new one — add on top, like every other rail.

⚠ THE CHALLENGE WEARS A 200. After a burst of searches this store answers /search?q= with a 15 KB document titled "Robot or human?" and the cart with 412. Status alone cannot see the first, and reading its body as "no payload" says the same thing the rail would say for a store that genuinely returned nothing — which sends the user to an empty Choose Products screen for a store that never looked. So: 412 joins 418/429/403 as blocked, a 200 whose head says "Robot or human" is blocked, and the FIRST block stops the batch and hands over to the user. Searches are paced with a short random gap.

⚠ Open question, and the real one: a normal run does 6–14 searches in a burst, which is not far off what tripped this. A lighter search than a 780 KB document per term — the Next.js data route /_next/data/<buildId>/search.json — would be quieter AND faster. Unmeasured: by the time it was tried the session was challenged on the homepage too, so there was no buildId to read.

⚠ NO PRICE. The SSR payload carries priceInfo with every field empty and price: 0 on every item, so Walmart candidates reach the Choose Products screen without one. The only rail with this gap.

⚠ A rail may have NO STORE. The engine used to demand a storeId and a shoppingContext from every session, because the first four rails all have a catalogue that is per store. Walmart's search is national and its cart is the account's, so every run was handed to the user with session_no_store until the rail could say needsStoreId: false.

What is unique to Walmart

The dollar total is the only honest signal. Walmart's per-card stepper updates optimistically — it shows the new quantity before the server has agreed. The cart header's aria-label ("Cart contains N item Total Amount $X.XX") only moves after the API commits. So clickOnce reads both, and success is totalUp alone; the stepper reading is kept purely so that "stepper went up, total did not" shows up in the log as the smoking gun for a server rejection.

Login is decided by opening a menu. There is no cookie or endpoint to read, so the check clicks the hamburger, waits for the drawer, and looks for exactly two indicators. The both-or-neither case defaults to logged out on purpose — showing a login the user does not need is recoverable; running an add against a signed-out session is not.

The grid fills progressively, so a low card count is distrusted. A cold load can render two cards, hold long enough to look settled, then fill in the rest. The extractor accepts a healthy count (≥ 4) as soon as it is stable for two polls, but keeps polling ~3.6 s before it will believe a small one.

Three layers of card that are not results. Sponsored (sba-container) and "Explore related items" (carousel-container) use the identical product markup. The only thing that separates a real result is an ancestor with data-testid="item-stack", so every card walks up to 15 levels looking for it.

spaSearch defaults true and should stay true. Navigating to /search?q= fires onLoadEnd more than once while the search-and-add script is still running. Without the flag the engine re-injects and runs a duplicate add — which double-adds, then the next item's navigation race-cancels the cart POST so the item reverts to zero, and overwrites the next item's result slot so that item is skipped.

incBtn[data-testid="quantity-stepper-inc-button"]

All four ship as fallbacks in SEL_FALLBACKS and are overridden live from the remote automation config — a Walmart redesign is a config push, not an App Store release. They are read inside a build function, never at module scope, because the remote config lands after import and a module-scope capture would freeze the fallbacks forever.
