Wegmans add-to-cart automation

WEGMANS HAS A RAIL (2026-09-03)

And its search is the fastest of any store here, because it needs no session at all. Researched against a live signed-in session before a line was written — see docs/network-rail-research/01-wegmans.md.

PhaseHowMeasured

⚠ The search ENDPOINT needs no session — but the search does. An earlier version of this page said otherwise. Algolia is open, but the query has to be filtered to the user's STORE, and MEASURED 2026-09-03 the store number is not in any cookie, in localStorage, in the server HTML of / or /shop, or behind any of four plausible /api paths (all 404). It arrives with the customer profile, behind the bearer. Unfiltered, the query returns every store's catalogue — real products under real names carrying ids that are not valid where this user shops. So the rail REFUSES to search without a store number and caches it for a day once anything learns it.

The bearer is READABLE, 2026-09-03. This said the opposite for a fortnight, and the rail waited for a capture that could never happen — it takes the header off the site's own commerce call, and the rail runs on robots.txt where no site code ever runs. So Wegmans had no session at all: search answered 0 of 6 and the cart read said no_token.

MSAL's scheme, read out of their own bundle and confirmed on a device:

cookie msal.cache.encryption = { id, key }          32-byte key, base64
entry  msal.<...>            = { id, nonce, data }

salt = base64(entry.nonce)     the field is named nonce; it IS the salt
info = the clientId, but ONLY when the entry key contains it
aes  = HKDF-SHA256(cookie.key, salt, info) -> AES-GCM 256
iv   = TWELVE ZERO BYTES       not the stored nonce

Same-origin is all it needs, so the quiet page can do it: no network, no page load, nothing for the user to do. The clientId comes out of the STORAGE KEY rather than window.msal, which only exists on the shop app. A cache keyed on the JWT's own expiry still fronts it, and a 401 still forgets it.

And every commerce call needs ?api-version=. Without it the gateway rejects BEFORE it adds CORS headers, so the browser reports a bare "Failed to fetch" with no status — indistinguishable from a dead host, which is exactly the wrong conclusion this map used to draw. With it, /commerce/account/customer answers 200 in 302 ms.

The store number is in the CART, at grocery.custom.customFieldsRaw[] where name === 'storeNumber' — BY NAME, never by index. Nowhere else: not the customer profile (which carries only hasInstacartAccountsForStores), not storage, not a cookie, not the shop HTML. One call answers both halves, because that response IS the cart.

The write, 2026-09-03.

POST /commerce/cart/carts/lineitems?api-version=2024-02-19-preview
{ StoreKey, cartData:[{ cartID, cartVersion, custom, lineItems:[…] }], customerID, customerEmail }

lineitems, one word, on the collection. It could not be guessed: this gateway rejects an unknown route BEFORE adding CORS headers, so a wrong path and a dead host both read as a bare "Failed to fetch" — /carts/{id}, /carts/{id}/line-items, /carts/items, PUT and PATCH all "failed" identically. Watching the site add one item gave it immediately. StoreKey comes from /api/stores (same-origin, no token), the customer ref from the profile, and every line-item field from the Algolia row — looked up by objectID ("140-75994"), because skuId is in the index but is not a filterable facet and returns 0 hits for a sku that exists.

⚠ THE LINE ID DECIDES WHAT THE WRITE MEANS.

payloadwhat it does
no line idCREATES a line. For a sku the cart already holds it returns 200, advances the cart version, and changes nothing at all.
id of the existing lineSETS that line's quantity. Measured 1 → 2, then 2 → 3. The plain id field alone is enough.

So the add looks each item up in the baseline it just read: a line it finds is addressed by id and written held + wanted, exactly like every other rail; anything else is a new line at wanted. Cart writes add on top — an item already in the cart is not a special case and is never refused. It briefly was, having copied the Instacart guard, which exists there only because that store's write sets a line and its semantics were unmeasured.

Reading it as purely additive would have been just as wrong in the other direction: held + wanted sent to an adding endpoint gives held + held + wanted, which is the MEAL-194 over-add.

⚠ AN EXPIRED TOKEN IS NOT A SIGNED-OUT USER. The access token lasts an hour. MSAL renews it with the refresh token beside it in the same cache — but only where the site's own code runs, and the rail runs on robots.txt where it never does. So an hour after the user last opened Wegmans, every script reported no_token on a device holding a refresh token good for another six hours. The rail now does what MSAL does: grant_type=refresh_token to the B2C token endpoint, DISCOVERED from the authority's own public openid-configuration rather than assembled from guesses. The scope comes off the expired access token, the only record of what to ask for. The rotated refresh token is kept in our own storage and never written back into MSAL's encrypted cache.

⚠ PRICED by weight is not SOLD by weight. isSoldByWeight is true for both of these, so it cannot be the discriminator:

productonlineSellByUnitapproxprice
Butter Boy French ButterEach0.25 lb$6.48 a unit, quoted $25.89/lb
Fresh Sea Scallopslb0$32.99 a pound

The unit of SALE is the answer. Reading the flag asked the user to choose a weight for a block of butter you buy one of. The flag is still ECHOED to their API on a write — that field has to say what their index says — but it does not decide our screens.

⚠ A WRITE MUST NAME ITS CART. Sent without cartID and cartVersion the API does not fail — it CREATES A NEW CART, and the existing basket stops being the active one. The app passes knownLines (the prewarmed baseline: held quantities, no ids), the add skipped its own read on the strength of it, and a real 20-item basket became a one-item cart. The add now always reads the cart, and refuses if what it reads back has no id or version.

⚠ The product id is PER STORE. The same Daisy sour cream is 626485 at store 50 and 608294 at store 140, and unfiltered "sour cream" returns 32,223 hits — every store's catalogue at once. So the storeNumber filter is not optional, and a saved product carries its barcode as well as its id: the id does not survive a store change and the barcode does.

Wegmans is ASSISTED (2026-09-01)

DOM automation was removed from Mealio. Wegmans had no API or in-page rail behind it, so it no longer adds to the cart on the user's behalf: Mealio searches each ingredient and hands the user the results page; they add what they want and tap Next.

Everything below about extractors, add clicks, worker pools and selector drift is HISTORY. It is kept because it is the evidence for MEAL-213, which asks whether this store can have a real in-page rail like H-E-B and the Albertsons family — and because the login check and the search URL, which the assisted route still uses, are described here too.

Read off webview-scripts/wegmans.ts and the stores.wegmans entry in automation-config/schema.ts. Wegmans is the store where the WAF, not the markup, sets the shape of the run.

2026-09-04 — Amazon Fresh is gone. It was the last store with no network rail, so it could only search and hand the user the page to add from. Removed from the catalogue rather than carried as the one store Mealio cannot add to. Every store here now has a rail; the last DOM read in production went with it, and "assisted" is now a state a store passes through (rail off, or unable to answer) rather than what a store IS.

What is unique to Wegmans

Serial by force, and it is the WAF's decision. forceSerialSearch defaults true here: Wegmans's WAF 403s the concurrent worker searches, and even two staggered workers still got blocked. cacheBustNav defaults false for the same reason — the synthetic ?_t= query is itself a signal. The worker scripts (buildWegmansWorkerScript, workerCount: 2, workerStaggerMs: 400) are still built and exported so the parallel path can be retried later without archaeology; they simply are not reached at runtime.

The cache is consulted last, not first. A positive login detection is written to sessionStorage so it survives the MSAL bootstrap killing the script mid-page. That read used to sit at the top of the script as a fast path — and because nothing ever removed the entry, a mid-session logout left the header plainly reading "Sign In" while the cache kept answering true for the life of the WebView. SilentLoginProbe latches, so it never asked again; WebViewCartSheet waited for a LOGIN_STATUS:false that could no longer arrive. Every search and every add then ran signed out, with no login wall and no error. The order in diagram 2 is the fix: live detection always wins when it can read the button, the cache answers only when eight seconds of observing found no button at all, and a negative verdict actively clears a cached positive. 'out' is still never cached, so a post-sign-in re-check always runs fresh.

Albertsons carries the identical shape (MEAL-42 / MEAL-114) on purpose — change the two together.

One click means one click. robustClick dispatches the full pointer sequence because React's synthetic event system in a mobile WebView does not reliably see a bare .click(). It used to also call btn.click() unconditionally afterwards — so every call fired Wegmans's handler twice and a qty-1 request put 2 in the cart. The native call is now only a fallback for an environment with no PointerEvent constructor.

Clicks are settled, not batched. Wegmans's cart API is async and its optimistic update reconciles against the server response; clicking + again before that lands races the reconciliation and can visually reset the quantity to 0. Each increment waits.

The sticky header eats buttons. scrollIntoView({block:'center'}) alone left the add button behind the ~100 px sticky header — earlier runs logged a rect y of −36 — so scrollIntoCenter re-reads the rect and scrolls clear of it before clicking.
